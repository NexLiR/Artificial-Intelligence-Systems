# Текстова RPG на локальній моделі

Оповідач - локальна модель Qwen3-8B у LM Studio, а правила гри (HP, золото, інвентар, квест, кидки кубика) живуть у коді.

## Як запустити

1. Встановіть LM Studio і завантажте **Qwen3-8B** у форматі GGUF (Q4_K_M, Q8_0).
2. Завантажте модель з налаштуваннями: Context Length 8192, GPU Offload 36.
3. У розділі Developer (Local Server) запустіть сервер. Адреса за замовчуванням: `http://localhost:1234/v1`, потрібно увімкнути CORS.
4. У папці застосунку запустіть статичний сервер:

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

6. Відкрийте `http://localhost:8000`.

Модель перемикається списком у верхньому правому куті (Q4_K_M або Q8_0). Перемикання змінює лише ідентифікатор моделі в запитах: LM Studio має сама завантажити потрібну модель або її треба завантажити вручну. Інакше сервер поверне помилку, яка покаже назву моделі.

Параметри в адресі (для тестування): `?model=<назва>`, `?t=0` (temperature), `?schema=0` (вимкнути `response_format`, якщо рантайм його не підтримує).

## Як це працює

Модель не керує грою. Вона виконує дві вузькі ролі, а всі наслідки ходу визначає код.

- **Сценарій задає гравець.** Перед грою вводиться опис. Модель повертає JSON: назва квесту, 3-4 локації (перша стартова), 2-4 цілі з привʼязкою до локації, до 4 стартових предметів. Код перевіряє результат (обовʼязкові поля, ліміти, цілі лише в існуючих локаціях). Окремим текстовим запитом пишеться вступна сцена.
- **Стан гри в коді**, а не в історії чату: HP, інвентар, локація, цілі з прогресом, попередня сцена, 5 останніх подій. Події формує код.
- **Хід це два запити.**
  1. *Суддя* (JSON, temperature 0.1) оцінює дію гравця: чи можлива вона (немає предмета, магія, телепорт), чи небезпечна, яку ціль просуває, який предмет витрачено чи знайдено, чи лікує.
  2. Код визначає наслідки.
  3. *Оповідач* (звичайний текст, temperature 0.7) описує вже визначений результат. Він отримує вердикт і список фактів, тому текст не може суперечити стану.
- **Що вирішує код:** вердикт за кидком d20 (1 критичний провал, 2-7 провал, 8-14 часткова удача, 15-19 успіх, 20 успіх із бонусом), шкода, лікування, перехід між локаціями (за назвою локації в тексті дії, а також «далі» і «назад», потрібен кидок 4 і більше), просування цілей (кидок 8 і більше, гравець у локації цілі, ціль виконується за 2 кроки), знайдені предмети (кидок 15 і більше).
- Твердження судді, які код не прийняв, показуються під відповіддю («відхилено»).
- Некоректний JSON або порожній текст: один повторний запит, потім зрозуміле повідомлення про помилку (хід не зараховується).
- HP 0 завершує гру, виконання всіх цілей дає перемогу. Стан зберігається в `localStorage`.

## Параметри генерації

- **temperature 0.7 для оповідача і сценарію**: оповідь має бути жвавою. **0.1 для судді**: це класифікація, потрібна стабільність.
- **max_tokens**: 400 для оповіді, 200 для судді (JSON зі схеми), 600 для сценарію, 250 для вступної сцени. Ліміти запобігають зацикленню малої моделі. Незавершене останнє речення обрізається.
- **Контекст 8192**: найбільший запит (оповідач) становить, за оцінкою, до 1-1.5 тис. токенів і не міняється.
- **Режим міркування вимкнено**.

## Тестування

У полі дії можна почати рядок з `[N]` (число 1-20), щоб задати кидок вручну, наприклад `[5] Намагаюся вкрасти гаманець`.

Порівняння моделей виконує окремий скрипт `demo/rpg_bench.mjs`. Він генерує сценарій за описом, потім проходить фіксований сценарій зачистки підземелля з 21 ходу із заданими кидками й записує текстовий протокол (з відповідями судді, фактами й текстом оповідача):

```bash
cd demo
node rpg_bench.mjs --model qwen3-8b@q4_k_m
node rpg_bench.mjs --model qwen3-8b@q8_0
```

Параметри: `--t` (temperature, за замовчуванням 0.7), `--schema 0`, `--base <url>`. Між запусками потрібно завантажити в LM Studio іншу модель.
